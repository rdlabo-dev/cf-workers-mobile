# Worker document loading in a native WebView

## Goal

Hono/TSX or Workers Express generates the HTML and owns routing. Capacitor should load that Response as a normal document, including ordinary links, history, module initialization, forms, and resource requests. The library must not introduce another application navigation framework.

This is a native integration experiment, **not a supported package API**. The ordinary demo and npm library are unchanged. The [earlier Turbo experiment](turbo-rendering-experiment.md) demonstrated that persistent-window HTML replacement changes application lifecycle; Turbo is not used by this experiment.

The later [ordinary-plugin connection investigation](document-connection-plan.md)
validates a way to avoid consumer Activity/ViewController replacements. The
custom-controller setup below is the earlier experiment, not the proposed public setup.

## Connection

```text
Visible Capacitor WebView: normal document / link / resource request
  → iOS WKURLSchemeHandler or Android Service Worker FetchEvent
  → offscreen WebView that stays alive across document navigation
  → existing workers-capacitor transport and dedicated Worker
  → Hono or Express Fetch Handler
  → Response bytes / status / headers
  → visible WebView's normal document loader
```

The offscreen WebView is only a runtime host. It does not render the application's UI and is not an iframe. It retains Web APIs and the existing Worker transport without reimplementing them in JavaScriptCore or another engine. This is a feasibility choice, not yet a decision to require a second WebView in the public library.

The visible WebView creates real documents without Turbo, DOM replacement, or link interception. On iOS only, an injected script handles JavaScript `fetch` separately from document navigation. Multipart POST forms are serialized before starting a native POST navigation to avoid losing file bytes. The native test driver is injected independently of the application pages.

The logical Worker origin remains `https://worker.invalid`. Native interception maps local paths/query strings to it, while the document retains `capacitor://localhost` on iOS and `https://localhost` on Android. Only local `/pages/` and `/api/` requests are intercepted in this fixture. Bundled CSS, images, modules, and bootstrap assets use Capacitor's normal asset handler. `/api/generated.js` also demonstrates a script resource generated by the Worker, requested by a normal `<script src>` element.

## Platform findings

- iOS: Capacitor already owns the `capacitor` scheme. Attempting to replace its registered handler throws an Objective-C exception, even after setting it to nil. The test controller creates a fresh configuration through Capacitor's public configuration factory, retains its bridge user-content controller, and registers a handler before creating the WebView. Asset requests delegate to the existing asset handler.
- Android: native `WebResourceRequest` has no request-body getter, and `WebResourceResponse` cannot represent redirects. Instead, a standard Service Worker receives the complete Request, passes its bytes to the persistent runtime host through a MessageChannel, and returns the Response. The browser handles form navigation and redirects. Capacitor's existing Service Worker asset handler serves the bundled bootstrap. No HTTP server is started.
- iOS: the custom `capacitor:` scheme cannot use that Service Worker path. The scheme handler reads `httpBody` or `httpBodyStream`. For main-document redirects it cancels the provisional request and loads the redirected native URLRequest, preserving POST/body for 307/308 and converting POST to GET for 301/302/303. Subresource redirects are followed in the runtime host. This is limited compatibility, not a complete Fetch redirect implementation.
- iOS JavaScript fetch: `page-fetch.ts` subclasses the existing public `FetchRuntime` for dispatch and adds experimental redirect handling. It reads the Request body before WebKit serialization, sends buffered bytes through `WKScriptMessageHandlerWithReply`, and receives the Worker response from the persistent host. The public FetchRuntime itself does not implement redirect following or response metadata; those additions are experiment-local.
- iOS multipart forms: `form-body.ts` supplements same-window local POST submissions. Native validation runs first; form/document submit handlers can cancel. The adapter builds `FormData(form, submitter)`, including application `formdata` changes, reads its bytes, then starts a native URLRequest POST. `form.submit()` is handled separately to retain its validation/event bypass. The resulting HTML is a new document. An earlier attempt to let submission continue while delivering bytes asynchronously raced with navigation and was removed.
- Express enables ETags. Its conditionally requested documents can return a bodyless 304, which this bridge does not resolve against a cache. The probe removes `If-None-Match`/`If-Modified-Since` and marks Worker responses `Cache-Control: no-store`. This changes cache semantics deliberately; it is not transparent HTTP cache compatibility.
- The runtime must outlive the visible document. A dedicated Worker owned by the navigated page is insufficient for this architecture.

References: [Apple WKURLSchemeHandler](https://developer.apple.com/documentation/webkit/wkurlschemehandler), [Android WebViewClient](<https://developer.android.com/reference/android/webkit/WebViewClient#shouldInterceptRequest(android.webkit.WebView,android.webkit.WebResourceRequest)>), [WebResourceRequest](https://developer.android.com/reference/android/webkit/WebResourceRequest), [WebResourceResponse](https://developer.android.com/reference/android/webkit/WebResourceResponse). Capacitor integration was inspected against the installed 8.5.3 source.

## Validation

The native test driver checks initial HTML, standards mode, inline/classic/module scripts, relative module imports, API fetch, bundled CSS/image, a fresh Window on ordinary navigation, module initialization on ordinary revisit and reload, back/forward, GET-form URL/escaping, a Worker-generated script resource, and a native CapacitorCookies round trip after navigation. It also checks URL-encoded POST forms (including duplicate fields and the submitter), 301/302/303/307/308 final URLs, methods, bodies and back history, JSON API requests through those redirects, and multipart file bytes.

Verified on 2026-10-16, after disabling HTTP caching in the bridge:

| Environment                      | Hono/TSX | Workers Express |
| -------------------------------- | -------- | --------------- |
| iOS 26.1 Simulator (split fetch) | 65/65    | 65/65           |
| Android 16 emulator              | 50/50    | 50/50           |

The initial native-only iOS baseline was 41/42 for both frameworks: multipart fetch returned HTTP 500. The split-fetch experiment verifies the initial 42 checks, 15 additional iOS Fetch redirect checks (five statuses × final metadata/clone, manual, error), and eight file-form checks. File forms cover direct navigation, 307/308 replay, a submitter action override, application formdata changes, direct `form.submit()`, and back history. Android has 50 checks; the extra 15 injected-Fetch checks are iOS-specific. Browser-style manual handling returns an opaque-redirect response (`status: 0`, empty headers, no body), not a readable 302 response. See the [Fetch Standard](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect).

### Where iOS loses upload bytes

The A/B diagnostic sends a four-byte binary file inside multipart data, with a Japanese text field. A raw echo endpoint measures bytes before form parsing; the scheme handler adds its own received-body byte count.

| Input / path                                                        | Scheme-handler bytes | Worker bytes | Exact encoded bytes |
| ------------------------------------------------------------------- | -------------------- | ------------ | ------------------- |
| Original native fetch with FormData                                 | 0                    | 0            | No                  |
| Original native fetch with a Blob of encoded multipart              | 0                    | 0            | No                  |
| Original native fetch with Uint8Array of the same encoded multipart | 306                  | 306          | Yes                 |
| Script-message fetch with the same Uint8Array                       | Not used             | 306          | Yes                 |

Thus the loss is already present at the native scheme-handler boundary, before the Worker or its multipart parser. The same content reaches the Worker intact when sent as bytes. The new script-message path also passes FormData directly through its Request serialization and verifies the file name, content type and all four file bytes. This isolates and bypasses the observed failure; it does not prove every WebKit upload issue has the same cause. The [WebKit Blob/custom-scheme report](https://bugs.webkit.org/show_bug.cgi?id=197237) describes a related unresolved issue.

The A/B table above concerns JavaScript `fetch(FormData)`. Separate native tests now assign a binary File to an actual `input[type=file]`, submit the HTML form and verify the new document, server-side decoded bytes, submitter and history. The OS file-picker UI and physical devices are not tested. iOS needs the injected multipart-form supplement; Android uses the normal Service Worker path.

The local workerd suite passed 21 tests, including both frameworks' POST/redirect behavior, multipart bytes, and Express ETag revalidation returning 304. The injected-script browser suite adds 36 checks across Chromium/WebKit and both frameworks. It uses the real dedicated Worker and mocks only native message delivery/navigation; native tests separately cover the actual WebView integration. It checks redirect modes, metadata/clone bodies, binary FormData, submitter overrides, formdata changes, validation/cancelled submission and direct submit.

The separate browser Service Worker comparison has 16 successful Chromium tests. Its WebKit comparison has 10 successes and **six known failures** marked with `test.fail`: POST bodies are lost on 307/308 replay and fetch redirect metadata differs, for both frameworks. Across both suites, Playwright accounts for 68 tests: 62 successes and six expected comparison failures. This does **not** mean 68 compatibility successes. Native iOS uses the scheme handler, not this browser Service Worker path.

The ordinary demo browser suite passed all eight regression tests. Demo typechecking and both runtime-host build modes also passed. Native outcomes are manual simulator/emulator runs, not GitHub Actions results. CI runs the browser comparison, builds the Express host variant, and runs the workerd suite, but does not run this native driver.

Reports appear in the visible page and at `localStorage['native-document-result']`; the state machine lives in sessionStorage so it survives document navigation. Start a fresh app process for each run. A previous report alone is not evidence: check the framework and current on-screen result. Evidence files live under ignored `demo/artifacts/native-documents-*` and `demo/artifacts/split-fetch-*-ios.json`. Each iOS runtime launch removes the previous native report to avoid mistaking an interrupted run for success. The iOS probe also writes `Documents/native-document-result.json` in the simulator app container; obtain the current container with `xcrun simctl get_app_container <device> jp.rdlabo.workerscapacitor.poc data` after each installation.

The workerd suite separately executes both Worker fixtures, including their generated script routes. It does not test native interception. The earlier Turbo implementation and dependencies were removed; only its investigation record remains.

## Unresolved boundaries

- URL-encoded form navigation, JSON fetch, and small file-containing FormData fetch are demonstrated. Small file-input form navigation is also demonstrated. Large uploads and other encodings are unverified. HEAD forwarding is implemented but not separately verified.
- Multipart supplementation is limited to same-window local POSTs. Named-window/iframe targets, overlapping submissions, and window-level submit listeners registered after the adapter need separate compatibility tests. It is not a general HTML form polyfill.
- External redirects are intentionally out of scope, not a planned compatibility gap. Local redirects are bounded at 20 hops. The native scheme path still cannot convey Fetch redirect mode; the injected JavaScript path handles it before native dispatch.
- The injected path models `url`, `redirected`, `type`, and `clone()` through JavaScript own properties. These checks establish ordinary property-access behavior only. They do not change browser-internal Response slots: prototype getter calls, header guards and use by other browser APIs are not full native Response compatibility. This remains experimental, not a complete Fetch implementation.
- Response streaming, repeated headers, cookies/auth, cancellation propagation to the Worker, downloads, and interaction with an application's own Service Worker need separate contracts and tests.
- Responses and request bodies are buffered; iOS additionally base64-encodes them. Memory, latency, concurrent load, host suspension/process termination, and teardown/recreation have not been characterized.
- Two WebViews add lifecycle and memory cost. The offscreen host has no Capacitor plugin bridge; Worker bindings requiring native plugins are not validated here.
- Scheme/origin differences, CSP, and application asset routing are not automatically solved by these checks.
- This uses simulator/emulator builds, not physical devices. It adds no HTTP listener and makes no cloud deployment.

## Reproduce

From `demo/`, after dependency installation and building the library:

```sh
npm run test:native:prepare -- native-documents hono
npm run sync
node tests/scripts/native-document-overlay.mjs apply
npm run ios # or npm run android
# Inspect the final native-document-report in the page.
# Repeat prepare/sync/build with "express". Apply the native overlay only once.

# Always restore the normal native entry points and demo assets afterwards:
node tests/scripts/native-document-overlay.mjs restore
npm run build
npm run sync

npm run test:documents
npx vitest run --config tests/vitest.config.ts tests/workers/rendering.test.ts
```

The overlay stores original native entry files under `demo/artifacts/native-document-originals/` and refuses a second apply. It temporarily replaces Android's MainActivity and appends the iOS test controller to SceneDelegate; restoration does not use git reset. Do not edit those two native entry files while the overlay is active. All experimental sources are under `demo/tests/`.

The Android probe unregisters its Service Worker after completing the report. If a run is interrupted before completion, unregister it through WebView DevTools (or clear this test app's storage) before restoring the ordinary demo; restoring files alone does not remove browser registrations.

## Current library transport update

The current `src/runtime/documents` / `native/ios/DocumentBridge.swift` transport returns
headers before response EOF and pulls at most 64 KiB per native reply. Android's
Service Worker uses the same host pull/cancel commands. Cancellation, disposal,
and native navigation stop release response readers and abort request signals.
The historical experiment observations above describe its earlier buffered code.
Native document uploads remain bounded buffers (8 MiB maximum); Fetch-only Worker
uploads use streaming. Legacy buffered native response callers are limited to
8 MiB and should update with the library. Local unit and native build evidence
must not be treated as physical-device peak-memory measurements.
